The project is a Java production-style service for:

1. Storing purchase transactions.
2. Retrieving stored purchases converted to a target currency using Treasury Reporting Rates of Exchange.
3. Applying the business rule that the exchange rate must be less than or equal to the purchase date and no older than six months.
4. Returning a clear domain error if no eligible rate exists.
5. Being fully runnable locally without separately installed databases, web servers, or servlet containers.

## 5. Core functional requirements

### Store purchase

The API must accept and persist:

- description
- transaction date
- purchase amount in USD

Rules:

- `description`: required, max 50 characters
- `transactionDate`: required, valid date
- `amountUsd`: required, positive, validated to scale 2 (no implicit rounding of inbound payload)
- `id`: generated by server and globally unique

Use `BigDecimal` for all money and exchange-rate calculations. Never use `double` or `float` for money.

### Retrieve converted purchase

The API must retrieve a stored purchase and return:

- identifier
- description
- transaction date
- original USD amount
- target currency
- exchange rate used
- exchange rate date
- converted amount

Exchange-rate rule:

```
Use the most recent Treasury exchange rate for the target currency where:
  rate.record_date <= purchase.transactionDate
  AND
  rate.record_date >= purchase.transactionDate minus 6 months (calendar)
```

If no eligible rate exists, return a domain error:

```
CONVERSION_RATE_NOT_AVAILABLE
```

The converted amount must be rounded to two decimal places. Use an explicit rounding mode. **Project default: `RoundingMode.HALF_UP`** (documented in ADR-0001).

## 6. API design rules

Use versioned REST APIs. Required endpoints:

```
POST /api/v1/purchases
GET  /api/v1/purchases/{id}/conversion?currency={currencyIdentifier}
```

`currencyIdentifier` accepts either:

- Treasury `country_currency_desc` (e.g., `Canada-Dollar`), case-insensitive
- ISO 4217 code (e.g., `CAD`), resolved via a curated alias table that maps to one canonical `country_currency_desc`

Ambiguous or unknown identifiers return `400 INVALID_CURRENCY`.

Create-purchase request:

```json
{
  "description": "Office supplies",
  "transactionDate": "2026-05-14",
  "amountUsd": "123.45"
}
```

Create-purchase response (`201 Created`, `Location: /api/v1/purchases/{id}`):

```json
{
  "id": "01HXZ7R7R7K7V9R8Z7R5Q7A1BC",
  "description": "Office supplies",
  "transactionDate": "2026-05-14",
  "amountUsd": "123.45"
}
```

Conversion response (`200 OK`):

```json
{
  "id": "01HXZ7R7R7K7V9R8Z7R5Q7A1BC",
  "description": "Office supplies",
  "transactionDate": "2026-05-14",
  "amountUsd": "123.45",
  "targetCurrency": "Canada-Dollar",
  "exchangeRate": "1.3700",
  "exchangeRateDate": "2026-03-31",
  "convertedAmount": "169.13"
}
```

Errors follow **RFC 9457 Problem Details** with extension members `errorCode` and `details`:

Error responses carry `Content-Type: application/problem+json` on the wire. Conformance is asserted by AC-T-5 across the full error-code matrix.

```json
{
  "type": "https://wex.example/problems/conversion-rate-not-available",
  "title": "Conversion rate not available",
  "status": 422,
  "detail": "Purchase cannot be converted to the target currency because no Treasury exchange rate exists within 6 months on or before the purchase date.",
  "instance": "/api/v1/purchases/01HXZ7…/conversion",
  "errorCode": "CONVERSION_RATE_NOT_AVAILABLE",
  "details": {
    "purchaseDate": "2026-05-14",
    "targetCurrency": "Canada-Dollar"
  }
}
```

## 7. Persistence design rules

Local runnable: H2 embedded, file mode, no external DB/servlet container, single-command start.

Production profile: PostgreSQL-compatible. JPA mappings must not encode H2-specific behaviour.

Tables: `purchase_transactions`, `exchange_rates`.

`purchase_transactions` columns: `id`, `description`, `transaction_date`, `amount_usd`, `created_at`, `updated_at`.

`exchange_rates` columns: `country_currency_desc`, `record_date`, `effective_date`, `exchange_rate`, `source`, `fetched_at`.

When Treasury republishes a rate for an existing `(country_currency_desc, record_date)`, the persistence layer stores the new revision as a **separate row** keyed by the triple `(country_currency_desc, record_date, effective_date)`. Previously-persisted rows are not mutated. The eligible-rate query selects max(`effective_date`) for the eligible `record_date`. (Closes G-P0-4 / A-018 / AC-026b / OQ-021 / R-027.)

Indexes:

- `purchase_transactions(id)` (PK)
- `exchange_rates(country_currency_desc, record_date DESC, effective_date DESC)`
- `pk(country_currency_desc, record_date, effective_date)` — composite primary key, replaces the surrogate `id` per Phase-4 grill G4-P1-4.

The converted amount is never stored as source of truth; it is computed at retrieval time.

## 8. Treasury integration rules

**Rate orientation invariant.** Treasury's `exchange_rate` direction (`USD → foreign-units` vs `foreign-units → USD`) shall be empirically verified against the live Treasury dataset for at least three currencies of known canonical cross-rate before ADR-0001 is signed. The verified orientation is recorded in ADR-0001; a contract test fails if the dataset's documented per-record convention diverges from the verified orientation. (Closes G-P0-1 / OQ-017 / R-021.)

Lookup order on conversion:

1. Look up an eligible rate in the local `exchange_rates` table.
2. If found, use it.
3. If not, call Treasury Fiscal Data API with single-flight de-duplication.
4. Validate and persist returned rates.
5. Re-evaluate eligibility locally.
6. If still no eligible rate, return `CONVERSION_RATE_NOT_AVAILABLE`.

The Treasury client must have: bounded connect/read timeout, bounded retries with backoff, circuit breaker, schema validation, structured logs, metrics, and explicit error mapping. Treasury outage with a usable local rate must succeed. Treasury outage with no eligible local rate returns `503 UPSTREAM_UNAVAILABLE` (Problem Details), never `CONVERSION_RATE_NOT_AVAILABLE`.

## 9. Reliability and resilience rules

Stateless app layer. Production design must support multiple replicas, load balancer/gateway, rolling deploys, graceful shutdown, readiness/liveness checks, DB-backed durability, and external-dependency fallback via locally persisted rates.

Failure modes to address explicitly: Treasury unavailable, Treasury timeout, Treasury malformed response, unsupported currency, no rate within 6 months, database unavailable, duplicate inbound request (idempotency-key optional, P1), invalid input, unexpected internal error.

## 10. Scalability rules

No microservices. Stateless app tier, DB indexes for lookup paths, connection pooling, rate persistence, optional in-memory cache for hot-path rate lookups, bounded outbound API calls, pagination-aware Treasury client. Cache exchange rates only; never cache conversion results.

## 11. Observability rules

Health endpoints: `/actuator/health`, `/actuator/health/liveness`, `/actuator/health/readiness`, `/actuator/metrics`.

Structured log events (non-exhaustive): `purchase_created`, `purchase_validation_failed`, `purchase_conversion_requested`, `purchase_conversion_completed`, `purchase_conversion_failed`, `exchange_rate_cache_hit`, `exchange_rate_cache_miss`, `treasury_api_request`, `treasury_api_success`, `treasury_api_failure`, `treasury_api_timeout`, `treasury_circuit_open`.

Metrics (non-exhaustive): `purchase.create.success.count`, `purchase.create.validation_error.count{reason}` (with `reason` ∈ `length|format|positive_required|scale_exceeded|future_date|pan_pattern|track1|track2|luhn-encoded|required`), `purchase.conversion.success.count`, `purchase.conversion.failure.count`, `purchase.conversion.unavailable_rate.count`, `exchange_rate.lookup.success.count`, `exchange_rate.lookup.miss.count`, `exchange_rate.cache.hit.count`, `exchange_rate.cache.miss.count`, `treasury.client.request.count`, `treasury.api.failure.count{reason}` (with `reason` ∈ `timeout|circuit_open|http_5xx|http_4xx|malformed|rate_sanity|orientation_drift`), `treasury.client.timeout.count`, `treasury.client.circuit_open.count`, `http.server.requests`, `db.connection.pool.active`, `currency_alias.drift.detected.count`.

Cardinality budget: default RED counters do **not** carry the `currency` label. Per-currency latency is exposed only on a separately-named histogram `exchange_rate.lookup.duration_by_currency` with a configurable allow-list. Combined cardinality budget ≤ 5 000 active series. (Closes G-P1-3 / G-P1-7.)

Correlation/request ID required. No secrets, no sensitive payment data, no raw untrusted input in logs (`description` is logged only as length + non-reversible HMAC hash).

## 12. Security and PCI-aware rules

This service must remain **outside PCI CDE scope**. Required practices:

- No PAN/SAD/CVV/track data/PIN/payment credentials anywhere.
- A **PAN-pattern content guard** is applied at the API boundary on the free-text `description` field: requests containing strings matching common PAN patterns (Luhn-valid 13–19-digit sequences with optional separators) are rejected with `400 PAN_PATTERN_DETECTED`, audit-logged, and counted.
- If future changes introduce PCI-sensitive data, stop and require a PCI design review before implementation.

Standard practices: server-side validation, RFC 9457 errors with no stack traces, no committed secrets, HTTPS-terminating ingress assumed for production, dependency vulnerability scanning, least-privilege DB access, input length limits, safe JSON deserialisation, structured exception handling.

**Description-hash logging.** The HMAC-SHA-256 key used to log `description.hash` is loaded from the env var `WEX_LOG_HASH_KEY`. Mandatory in `prod` / `staging` (service refuses to start on absence). Documented no-op fallback in `local` / `test`. The digest output carries a `vN:` version prefix (e.g., `v1:<hex>`) so pre/post-rotation digests are distinguishable. The key value is never committed to source, never logged, never echoed in error responses. Rotation policy in `docs/security/secrets-policy.md`. (Closes G-P1-4 / OQ-019 / R-023.)

Per the project's PCI posture decision, scope reduction is itself a deliverable: `docs/security/pci-scope-and-cde.md`, `cardholder-data-flow.md`, `cardholder-data-classification.md`, and `pci-security-grill.md` will formally evidence the out-of-CDE claim and adversarially attack it.
