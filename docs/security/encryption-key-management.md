# Encryption and Key Management

> **Status:** Phase 7 (PCI Security Design Session), 2026-05-17.
> **Owner:** SecArch.
> Closes **G4-P1-11** (HMAC key sourcing in production).
>
> Records every cryptographic asset the service has, where its key material lives, how it's generated/rotated/destroyed, and what evidence supports it.

## 2. Cryptographic primitives in use

| Use | Primitive | Library | Notes |
|---|---|---|---|
| Description-hash logging | HMAC-SHA-256 with ≥ 256-bit key (NFR-013b) | JDK `javax.crypto.Mac` (standard) | Non-reversible; correlates within a key version (`vN:` prefix); rotation tags break correlation across versions, which is fine — search filters by tag |
| TLS (inbound) | TLS 1.3 (preferred) / TLS 1.2 (minimum) | Platform ingress (e.g., nginx, Envoy) — not the JVM | NFR-011 |
| TLS (outbound, Treasury) | TLS 1.3 / 1.2 minimum; cert pinning to public CA bundle | JDK default `SSLSocketFactory`; configurable trust store | NFR-012 |
| TLS (outbound, DB) | TLS 1.2+ to PostgreSQL with `sslmode=verify-full` | JDBC driver default | DB-platform-managed |

The service does **not** implement:
- Symmetric encryption of stored data (no PAN/SAD to protect; DB-engine encryption at rest covers everything else).
- Asymmetric crypto for any application-layer purpose.
- Key derivation beyond HMAC-SHA-256 with a fixed-version key.

## 3. Key management requirements

### 3.1 Key generation

| Key | Generation method |
|---|---|
| `WEX_LOG_HASH_KEY` | `openssl rand -hex 32` (256 bits) or platform-equivalent. Generated by SecArch + stored in Vault before the first prod release |
| DB credentials | Platform-managed (DB-platform IAM) |
| TLS certs | Platform-managed (ACME / cert manager) |

### 3.2 Key storage — production retrieval pattern (closes G4-P1-11)

**Pattern selected:** **mounted secret file via CSI driver** (recommended) **OR Vault Agent sidecar** (alternative). Both expose the secret as a file on disk readable only by the service's UID; the service reads at startup; the file is owned by the platform's secrets-management runtime, not by the Pod.

Why not plain env var in production:
- Env vars are visible to any process running as the same UID (via `/proc/<pid>/environ` on Linux).
- Env vars are sometimes captured by debug dumps, error-reports, and orchestration logs.
- A mounted file with `0400` permissions has a smaller leak surface.

**Local / case-study mode** continues to support plain env var (`WEX_LOG_HASH_KEY`) — acceptable because no real secrets exist locally; the documented no-op fallback (`v0:`) is used if the env var is unset.

Implementation contract (Phase 13):
1. The service reads from a path indicated by `WEX_LOG_HASH_KEY_PATH` (defaults to `/var/run/secrets/wex/log-hash-key`) **first**. If that file exists, its content is the key.
2. If the file does not exist, fall back to `WEX_LOG_HASH_KEY` env var.
3. If neither is set: in `prod` / `staging`, refuse-to-start; in `local` / `test`, use the documented `v0:` no-op fallback.

### 3.3 Key rotation

| Trigger | Action |
|---|---|
| Scheduled — quarterly | SecArch generates new key; updates secrets store with new version (e.g., `v2`); deploys (rolling); confirms `log_hash_key_rotation_detected` event lands |
| Suspected compromise | Same procedure, immediately; old key revoked; incident-response process opens (Phase-7 [incident-response-pci.md](incident-response-pci.md)) |
| On staff offboarding (key-holder role) | Same as suspected compromise |

The rotation is **non-disruptive**: pre-rotation digests are `vN:`-prefixed and remain in the audit log indefinitely; post-rotation digests are `vN+1:`-prefixed. Log search for a specific description-hash must filter by version tag.

### 3.4 Key destruction

| Key | Destruction method |
|---|---|
| Previous `WEX_LOG_HASH_KEY` versions | After 1 year retention (matches audit-log retention), the key version is destroyed in the secrets store. Audit logs with `vN:<hex>` digests outlast destruction but become uninvertible by design. |
| DB credentials | Per platform policy. |
| TLS certs | Per platform policy (typically rotated and the old cert revoked). |

### 3.5 Separation of duties

| Role | Can do | Cannot do |
|---|---|---|
| SecArch | Generate keys; rotate keys; revoke keys; access secrets store as **read-write** | Read application logs / databases unsupervised |
| SRE (on-call) | Read application logs / metrics; trigger rotation procedure (initiates SecArch action) | Generate or read raw keys |
| Service-runtime IAM | Read `WEX_LOG_HASH_KEY` once at startup from the mounted file | Read DB credentials directly (loaded from a different secret path); cannot read other services' secrets |
| Auditor / Compliance | Read audit logs; read evidence-register; read rotation log | Read keys; modify keys |

### 3.6 Dual control / split knowledge

Not applied at v1 — single-secret design with single-rotator (SecArch). If the deployment grows to multi-team or a payment-processing requirement emerges, dual-control becomes appropriate (e.g., two SecArch operators required to rotate; key-share scheme).

### 3.7 Emergency access

If `WEX_LOG_HASH_KEY` is lost (secrets store outage; key file corrupted):
1. Service refuses-to-start (`prod` / `staging`) → A-026 alerts.
2. SecArch generates a replacement key.
3. Deploy proceeds.
4. **Pre-incident audit-log digests cannot be regenerated** — but they are already in the audit log, so correlation queries by the old `vN:` prefix continue to work; only new digests are computed.

There is no "break-glass" path that bypasses the key check in `prod` — fail-closed.

### 3.8 Audit logging

| Event | Where logged |
|---|---|
| `WEX_LOG_HASH_KEY` read at startup | `service_started` event includes `logHashKeyVersion` |
| Key rotation observed (first digest with `vN+1:` prefix after `vN`) | `log_hash_key_rotation_detected` event ([observability.md §2.2](../operations/observability.md)) |
| Secret-store access (any read of any key) | Platform-managed audit log; PCI Req 10 |
| Failed-to-start due to missing key | A-026 alert + `ApplicationContextException` log |
